# Governance and Validation

This document defines the standing quality bar for the Kurdistan Protocol
Compiler: the validation gates a change must pass, the architectural boundaries
that are enforced in code, and how the generated status is kept honest. It
describes process, not milestones; milestone specifications live in the KIP
documents under `docs/`.

## Validation bar

Every change must leave the tree passing all of the following. These are the
authoritative gates; a green result means each of them passed, not that a
subset was spot-checked.

| Gate | Command | Green means |
| --- | --- | --- |
| Build | `go build ./...` | compiles |
| Vet | `go vet ./...` | no vet findings |
| Format | `gofmt -l .` | empty (see line-endings note) |
| Tests | `go test ./...` | all package tests pass |
| Audit (quick) | `kcheck --quick --out <json> --status STATUS.md` | `Conclusion: passed`, gate set unchanged |
| Audit (full) | `kcheck --full --out <json> --status STATUS.md` | as above, full mode |
| Regression | `kcheck compare --a <baseline.json> --b <new.json>` | no regression beyond thresholds |
| Generated backend | `kgen --profile <p.json> --out <dir> && (cd <dir> && go test ./...)` | the emitted profile module builds and tests |

A single command runs the whole bar (build, vet, test, and the audit), for use
as a pre-merge check in the absence of external CI:

```
go run ./cmd/gate          # build + vet + test + full audit
go run ./cmd/gate -quick   # build + vet + test + quick audit (faster)
```

It exits non-zero if any step fails.

`STATUS.md` is generated by `kcheck`; it is not edited by hand. Regenerate it
whenever the audit gate set or its results change, so the committed status
always reflects the code.

## Enforced architectural boundaries

These are not conventions — they fail tests when violated:

- **Contract / model isolation.** The product runtime and real libraries must
  not import the quarantined `internal/contracts/**` or `internal/product/**`
  trees. Only the analysis/generation tooling (`internal/audit`,
  `internal/codegen`, `cmd/kcheck`) and the contract/product packages
  themselves may. Enforced by `internal/testkit/importrules`.
- **Behaviour baseline.** `internal/characterization` pins the observable output
  of the real protocol pipeline (profile hashes, first-frame bytes) for a fixed
  seed set. A change that alters this output is a behaviour change and must be a
  deliberate, reviewed golden update (`go test ./internal/characterization -update`),
  not an incidental drift.
- **Loopback only.** Runtime network addresses are restricted to loopback; no
  payloads, keys, proofs, or destinations appear in traces. See `docs/safety.md`.

## Gate discipline (review checkpoints)

Substantial work passes through explicit checkpoints before it is considered
done:

- **Intake** — the change's goal, scope, and non-goals are agreed, and any
  assumption that is load-bearing is recorded, not left implicit.
- **Plan review** — for multi-step work, the plan is checked for internal
  contradictions and for claims presented as fact without evidence.
- **Per-unit gate** — each self-contained unit of work passes the validation bar
  above before the next begins.
- **Slice review** — a security-relevant gate must actually fail when the defect
  it names is injected (mutation-proves-detection); a gate that cannot fail is
  not a gate.
- **Post-change** — `STATUS.md` is regenerated and docs are reconciled with the
  code.

## KIP ↔ work-order bridge and milestone numbering (D-007)

Milestone specifications live in the `docs/KIP-*.md` documents; planning and
execution are tracked as work orders. To keep the two in step:

- **Every new KIP** carries, near its top, a `status` and `last_verified` stamp
  and a short **Work orders** line referencing the work-order IDs that implement
  or verify it. Existing KIPs adopt this the next time they are edited; they are
  not mass-rewritten for it.
- **Milestone numbering is frozen, not renumbered.** The historical `M1`–`M59`
  numbers are load-bearing: the `adaptivepath_roadmap_public_docs` gate pins
  specific milestone strings (for example `M27: adaptive path model and candidate
  taxonomy`), and the KIP filenames encode their numbers. Re-numbering them would
  break gates and churn every KIP for no behavioural gain. The D-007 re-baseline
  is therefore **forward-only**: new milestones continue the existing sequence and
  reference their work orders; the historical numbers stay as recorded.
- A KIP and its milestone are **model/contract-level** unless a KIP explicitly
  states a `[live]` capability. The `[live]`/`[model]`/`[plan]` legend in
  `README.md` and `STATUS.md` is the single source of truth for what is real.

## Staleness

Plans, docs, and status decay from the moment they are written. On resuming
work, re-verify before acting: re-run the validation bar, confirm the current
`git rev-parse HEAD`, and treat any fact carried over from a previous session as
an assumption until re-checked. `STATUS.md` and the KIP documents should carry a
last-verified stamp when practical.

## Line endings

The repository stores text as LF (`.gitattributes`, `* text=auto eol=lf`).
`gofmt`, the build, and the tests are the source of truth for formatting. On a
Windows checkout configured with `core.autocrlf=true`, the working tree may hold
CRLF bytes that Git treats as equivalent to the LF blobs; this is a local
artifact and does not affect the committed content or a fresh checkout.

## Security-sensitive changes

Changes to cryptographic behaviour (`internal/crypto/**`), to what the runtime
enforces, or to the meaning of a security gate are held to a higher bar: they
require explicit review and, for production cryptography, external cryptographic
review before merge. The current suite is test-only and lab-scoped; see
`docs/safety.md` and the relevant KIPs.
